From Problem to Classes
● ~15 minutes

In the last pre-learning you met the vocabulary of OOP. Now you will use it to solve a problem. Before any code is written, a programmer reads the problem description and decides which classes are needed, what data each one must store and what each one must be able to do. Getting this design right makes the code much easier to write.

The scenario used throughout this page
A school library lends books and DVDs to students. Every item has a title and a unique item ID, and the library must record whether it is currently on loan. Books also have an author; DVDs have a running time in minutes. Books can be borrowed for 21 days and DVDs for 7 days. Staff need to add new items, find an item by its ID, let students borrow and return items, and count how many items are on loan.
Nouns → classes or attributes

A noun that has its own data and behaviour becomes a class (library, book, DVD). A noun that is just a single value describing something becomes an attribute (title, item ID, author, on loan).

Verbs → methods

Actions in the description become methods of the class that performs them or owns the data: borrow and return belong to an item; add, find and count belong to the library.

Ignore the noise: not every noun becomes part of the design. "School" and "students" are mentioned, but the program never stores any data about them, so they are not needed here.

Designing a Class
● ~15 minutes

Once the classes are chosen, each one is designed in detail. We start with a single Book class (DVDs are added in Section 4). For each class, decide:

1. Attributes & data types
What must each object store, and what type is each value? Make every attribute private.
2. Constructor
Which values are passed in when the object is made, and which start with a fixed default value?
3. Methods
Which getters and setters are needed, and which other methods carry out the actions in the scenario?
Book
- Title : STRING
- ItemID : STRING
- Author : STRING
- OnLoan : BOOLEAN
+ Constructor(Title, ItemID, Author)
+ GetTitle() : STRING
+ GetAuthor() : STRING
+ IsOnLoan() : BOOLEAN
+ Borrow() : BOOLEAN
+ ReturnBook()
Design decisions
  • ItemID is a STRING, not an INTEGER — it is an identifier like "B01", never used in calculations.
  • OnLoan is a BOOLEAN — an item is either on loan or not.
  • The constructor takes Title, ItemID and Author, but OnLoan always starts as False, so it is not a parameter.
  • Borrow() returns TRUE if the loan worked, or FALSE if the book was already on loan.
  • No setter for Title or ItemID — they should never change after the book is created.
Reading a class diagram line: + Borrow() : BOOLEAN means a public method called Borrow, taking no parameters (other than self) and returning a Boolean. - OnLoan : BOOLEAN means a private attribute holding a Boolean.
Good design rules: keep attributes private; give every attribute that outside code needs to read a getter; only add setters where a value really should change; and put each method in the class that owns the data it uses.

Python — the Book class
class Book: def __init__(self, Title, ItemID, Author): self.__Title = Title self.__ItemID = ItemID self.__Author = Author self.__OnLoan = False # default def GetTitle(self): return self.__Title def GetAuthor(self): return self.__Author def IsOnLoan(self): return self.__OnLoan def Borrow(self): if self.__OnLoan: return False # on loan self.__OnLoan = True return True def ReturnBook(self): self.__OnLoan = False
Main program — using the class
MyBook = Book("Dune", "B01", "Herbert") if MyBook.Borrow(): print(MyBook.GetTitle(), "borrowed") else: print("Already on loan") MyBook.ReturnBook()
Things to notice
  • Every method has self as its first parameter.
  • Every attribute is written self.__Name — the double underscore makes it private.
  • Borrow() returns a value, so the main program can test it with if.
  • Methods are called on an object (MyBook), not on the class name.
Setters with validation: where a value may change, the setter checks it first. For example, a Session's maximum size must be positive: def SetMaxSize(self, NewSize): then if NewSize > 0: self.__MaxSize = NewSize.
Exam tip: when asked to "write the class", examiners look for: the class header, a constructor with the correct parameters, every attribute declared private and initialised, and each requested method with the correct parameters and return value.

Designing with Inheritance
● ~15 minutes

The library also lends DVDs. A DVD has a title, an item ID and an on-loan status, and it can be borrowed and returned — exactly like a book. Writing a separate DVD class that repeats all this code would be wasteful. Instead, the design is refactored: everything that books and DVDs share moves into a superclass, and each subclass keeps only what is special about it.

LibraryItem
- Title : STRING
- ItemID : STRING
- OnLoan : BOOLEAN
+ Constructor(Title, ItemID)
+ GetTitle() : STRING
+ GetItemID() : STRING
+ IsOnLoan() : BOOLEAN
+ Borrow() : BOOLEAN
+ ReturnItem()
+ GetLoanDays() : INTEGER
△
inherit from LibraryItem
Book
- Author : STRING
+ GetAuthor()
+ GetLoanDays()
DVD
- Minutes : INTEGER
+ GetMinutes()
+ GetLoanDays()
How the design was decided
  1. List the attributes and methods of each class.
  2. Anything that appears in both moves up into the superclass.
  3. Anything only one class needs stays in that subclass (Author, Minutes).
  4. Behaviour that is shared but works differently — the loan period — is given a default in the superclass and overridden in each subclass (21 days for books, 7 for DVDs).
  5. Check the "is-a" test: a Book is a LibraryItem; a DVD is a LibraryItem. ✓
Python — superclass and two subclasses
class LibraryItem: def __init__(self, Title, ItemID): self.__Title = Title self.__ItemID = ItemID self.__OnLoan = False # GetTitle, GetItemID, IsOnLoan, Borrow and ReturnItem as before ... def GetLoanDays(self): return 14 # default class Book(LibraryItem): def __init__(self, Title, ItemID, Author): super().__init__(Title, ItemID) self.__Author = Author def GetAuthor(self): return self.__Author def GetLoanDays(self): # overrides return 21 class DVD(LibraryItem): def __init__(self, Title, ItemID, Minutes): super().__init__(Title, ItemID) self.__Minutes = Minutes def GetMinutes(self): return self.__Minutes def GetLoanDays(self): # overrides return 7
Benefit of this design: Borrow() and ReturnItem() are written once and work for every kind of item. Adding a new type later — say, Magazine with a 3-day loan — only needs a small subclass that overrides GetLoanDays().

Designing with Containment
● ~15 minutes

The final class in the design is Library. A library is not a kind of item — it has many items. So Library uses containment: it stores a list of LibraryItem objects as a private attribute, and its methods work through that list.

Library
- Items : list
+ AddItem(NewItem)
+ FindItem(ItemID)
+ CountOnLoan() : INTEGER
LibraryItem
…
Because Book, DVD and Magazine all inherit from LibraryItem, the same list can hold any mixture of them.
Python — the Library class
class Library: def __init__(self): self.__Items = [] def AddItem(self, NewItem): self.__Items.append(NewItem) def FindItem(self, ItemID): for Item in self.__Items: if Item.GetItemID() == ItemID: return Item return None # not found def CountOnLoan(self): Count = 0 for Item in self.__Items: if Item.IsOnLoan(): Count = Count + 1 return Count
Objects talk through methods

Library cannot read an item's private __OnLoan attribute. Instead it calls the item's public IsOnLoan() getter. Each class looks after its own data.

Returning an object

FindItem() returns the object itself, so the main program can call methods on it straight away: Lib.FindItem("D01").Borrow(). If nothing matches it returns None.

Watch out: in FindItem, return None must be after the loop. If it were inside the loop, the method would give up after checking only the first item.

Putting It All Together
● ~10 minutes

A complete OOP solution has two parts: the class definitions, and a main program that creates objects and calls their methods to solve the problem.

Python — main program for the library system
Lib = Library() Lib.AddItem(Book("Dune", "B01", "Herbert")) Lib.AddItem(DVD("Up", "D01", 96)) Lib.AddItem(Book("Holes", "B02", "Sachar")) SearchID = input("Enter item ID: ") Item = Lib.FindItem(SearchID) if Item == None: print("No item with that ID") elif Item.Borrow(): print(Item.GetTitle(), "is due back in", Item.GetLoanDays(), "days") else: print(Item.GetTitle(), "is already on loan")

MistakeWhat happensFix
Leaving out self in a method headerTypeError: method takes 0 positional arguments but 1 was givenMake self the first parameter
Writing __Title = Title in the constructorCreates a local variable; later an AttributeErrorWrite self.__Title = Title
Forgetting return in a getterThe method gives back NoneAdd return self.__Title

The design process in five steps: (1) pick out nouns and verbs; (2) decide which nouns are classes and which are attributes; (3) look for "is-a" and "has-a" relationships; (4) draw the class diagram with data types, constructors and methods; (5) write the classes and a main program, then test them.

✓ Summary — CIE 9618 Topic 20.1: Designing Classes & Writing OOP Code
Finding classes: nouns with their own data and behaviour become classes; single-value nouns become attributes; verbs become methods. Ignore nouns the program never needs.
Designing a class: choose private attributes and data types, decide constructor parameters and default values, then add getters, setters (with validation) and action methods.
Diagram to code: - Title : STRING → self.__Title; + GetTitle() : STRING → a method that returns it. Every method takes self.
Inheritance in design: move shared members into a superclass, keep special members in subclasses, and override methods whose behaviour differs (e.g. GetLoanDays).
Containment in design: a class that "has" many objects stores them in a private list and provides methods such as AddItem, FindItem and CountOnLoan that call the objects' public methods.
Main program: instantiate the objects, call their methods with dot notation, and use returned values (Booleans, objects or None) to decide what to do next.
